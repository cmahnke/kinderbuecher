# Implementor's guide: score-page TEI exchange format + IIIF setup

This document describes the on-disk exchange format this project produces
for OMR'd score pages — one TEI document per page, carrying the detected
staff regions and the MusicXML — and how it is wired into IIIF and the
viewer. It is written for anyone re-implementing the producer side (another
OMR engine, another book) or consuming the TEI/IIIF output in other tools.

## 1. The format: one TEI file per page

Each score page is one file, `public/<slug>/tei/<name>.tei.xml`, with three parts:

```
<TEI xmlns="http://www.tei-c.org/ns/1.0">
  <teiHeader>…</teiHeader>          <!-- source + OMR metadata -->
  <facsimile>…</facsimile>          <!-- staff geometry (the regions) -->
  <text><body>…</body></text>       <!-- the embedded MusicXML -->
</TEI>
```

Real example (abridged) for `page008` of "Vieilles Chansons et Danses et
Rondes":

```xml
<?xml version="1.0" encoding="UTF-8"?>
<TEI xmlns="http://www.tei-c.org/ns/1.0">
  <teiHeader>
    <fileDesc>
      <titleStmt>
        <title>Alltt moderato (Vieilles Chansons et Danses et Rondes, page008)</title>
        <respStmt>
          <resp>Encoded from the optical music recognition output of</resp>
          <name>homr</name>
        </respStmt>
      </titleStmt>
      <publicationStmt>
        <publisher>Projektemacher</publisher>
        <availability status="free">
          <p>Freely available for use and reuse. Generated by
          scripts/generate_tei.py from data/&lt;slug&gt;/results.json.</p>
        </availability>
      </publicationStmt>
      <sourceDesc>
        <bibl>
          <title>Vieilles Chansons et Danses et Rondes</title>
          <ptr target="…/page008/canvas"/>
        </bibl>
      </sourceDesc>
    </fileDesc>
    <encodingDesc>
      <appInfo>
        <application version="1" ident="homr">
          <label>homr</label>
          <p>Optical music recognition (homr) detected 3 staff(s) …</p>
        </application>
      </appInfo>
    </encodingDesc>
  </teiHeader>
  <facsimile>
    <surface ulx="0" uly="0" lrx="6228" lry="5185" corresp="…/page008/canvas">
      <graphic url="…/page008/info.json"/>
      <zone xml:id="page008-staff-1" type="staff"
            ulx="1427" uly="2228" lrx="5158" lry="2860">
        <path type="staff-line" points="1427,2231 1460,2231 …"/>
        <path type="staff-line" points="1427,2262 1460,2262 …"/>
        <!-- … one <path> per staff line (2×5 for a grand staff) … -->
      </zone>
      <!-- … one <zone> per detected staff … -->
    </surface>
  </facsimile>
  <text>
    <body>
      <div type="score">
        <score-partwise xmlns="" version="4.0">
          <work><work-title>Alltt moderato</work-title></work>
          <part-list>…</part-list>
          <part id="P1"><measure number="1">…</measure>…</part>
        </score-partwise>
      </div>
    </body>
  </text>
</TEI>
```

### 1.1 Coordinate system

All coordinates are **original image pixels**, origin top-left:

- `<surface @ulx/@uly/@lrx/@lry>` = the full page (`0, 0, width, height`).
- `<zone type="staff" @ulx/@uly/@lrx/@lry>` = the bounding box of one
  detected staff (= one system region of the scan). `xml:id` is
  `<name>-staff-<n>`.
- `<path type="staff-line" @points>` = one staff line as a polyline
  (`teidata.point` pairs: `x,y` integers, whitespace-separated, left to
  right). A grand staff contributes 10 paths (2 sub-staffs × 5 lines), a
  single staff 5. The paths are in line order, top to bottom — they are the
  staff grid: consumer code regroups point *j* across all paths into grid
  sample `{x, y[10]}` (see `src/tei.ts`).

### 1.2 Embedded MusicXML

The `<score-partwise>` tree inside `<div type="score">` is the OMR
engine's MusicXML **verbatim**, with two mechanical adjustments:

- its XML declaration and DOCTYPE are dropped (they cannot live inside
  another document — they are re-emittable on extraction);
- its root carries `xmlns=""`: MusicXML is namespace-free, and without the
  undeclaration the tree would fall into the TEI default namespace when
  parsed. The loose `pageNNN.musicxml` files already carry the same
  declaration (added by `scripts/run_homr.py`), so the embedded copy is
  byte-identical to the loose file from the root element on.

To extract a playable/renderable document: take the `score-partwise`
element, serialize it, prepend an XML declaration. The consumed XML is
namespace-free, exactly what OSMD and the playback parser expect.

### 1.3 Schema and validation

The format is defined by `schema/homr-tei.odd`, an official TEI ODD
customization: the standard TEI modules (`tei`, `header`, `core`,
`textstructure`, `transcr`, `linking`) plus a new no-namespace element
`score-partwise` (member of `model.common`, opaque content), tightened
`surface`/`zone` content models (required coordinates, `<graphic>` on the
surface, `<path>`-only staff zones), and three ISO Schematron
`<constraintSpec>`s (one surface per facsimile, ≥5 staff-line paths per
staff zone, exactly one embedded `score-partwise` in the score div).

`schema/homr-tei.rng` is the Relax NG compiled from that ODD with the
TEI's official ROMA/TEIGarage processor (see `schema/VENDORING.md` for the
exact command; recompile after any ODD change).

`scripts/validate_tei.py` enforces three namespace-aware layers with lxml:

1. Relax NG against `homr-tei.rng` (hard gate);
2. the compiled Schematron constraint patterns, extracted from the RNG and
   run as standalone ISO Schematron (hard gate);
3. the embedded MusicXML against the official MusicXML 4.0 XSD
   (`vendor/musicxml/`, **report-only** — see §4).

## 2. IIIF: pages reference the TEI, nothing more

Each book's manifest (`public/<slug>/manifest.json`, Presentation 3) is
deliberately **staff-free**; `public/books.json` (generated by
`scripts/generate_books_index.py`) indexes the books for the viewer's book
selector. Per page canvas:

- the painting annotation (IIIF image service) and the thumbnail — unchanged;
- OMR confidence/status/error as canvas metadata — unchanged;
- two **Alternative Representation** entries (`rendering`):
  `application/tei+xml` (`<slug>/tei/<name>.tei.xml`) and
  `application/vnd.recordare.musicxml+xml`
  (`<slug>/musicxml/<name>.musicxml`).

There are **no** staff annotations on the canvases. Staff regions are
resolved TEI-side: `<surface @corresp>` points at the page canvas URL, so
any IIIF consumer can walk from canvas → rendering TEI → surface → zones.
`public/` alone is deployable (static files, absolute URLs from a
configurable `--base-url`).

## 3. Viewer data flow

- The header's book selector is fed by `/books.json` (`public/books.json`,
  generated by `scripts/generate_books_index.py`). Switching books disposes
  the current detail/player view and rebuilds the overview grid from that
  book's manifest (`/<slug>/manifest.json`); the selection is remembered in
  `localStorage`. If `/books.json` is missing, the viewer falls back to the
  single root manifest `/manifest.json`.
- `src/manifest.ts` (`loadPages`) reads canvases into `PageResult`:
  image service, thumbnail, OMR metadata, and the `tei` rendering URL.
  `staves` starts empty — the manifest holds no geometry. Remote deployment
  URLs resolve relative to the directory the manifest was fetched from (the
  per-book folder), so per-book static files resolve in local/dev serving
  too.
- `src/main.ts` (detail view) fetches the page TEI and runs `parseTei`
  (`src/tei.ts`): zones → `StaffEntry[]` (bbox + rebuilt grid), embedded
  score → standalone MusicXML string. Overlays, the note-position mapping
  (`src/noteMap.ts`), the rendered score (`src/osmdRenderer.ts`) and
  playback (`src/playerPanel.ts`, `src/musicxml.ts`, `src/audio.ts`) all
  run off that parsed result; the overview badge backfills once parsed.
- The embedded MusicXML goes through the existing `sanitizeMusicXml()`
  (renders safe for OSMD) — the loose `MusicXML` rendering link in the
  detail view points at the plain file for download-only consumers.
- The player panel (`src/playerPanel.ts`) owns the playback controls: track
  and per-track instrument selectors, a **Dual** toggle (plays two staves at
  once; on by default when the score carries two note streams), and a
  **Score** toggle for the rendered-score overlay (off by default). The OSMD
  render always runs while anything consumes its alignment data (highlight
  rects, system mapping, cursor); the overlay itself mounts only while the
  toggle is on. Each rendered system maps exactly onto its staff region
  (`fit: 'none'`), so the notation fills the detected staves. In dual mode
  each playing track drives its own highlight set (staff rect, note marker,
  playhead), so the position shows on both staves.

## 4. Pipeline and setup

```
books/<slug>/pageNNN.jpg
  └─ scripts/run_homr.py ──→ data/<slug>/results.json + pageNNN.musicxml
        ├─ scripts/generate_tei.py ──→ public/<slug>/tei/pageNNN.tei.xml  (validated)
        └─ scripts/generate_iiif.py ──→ public/<slug>/<page>/ pyramids
  └─ scripts/generate_manifest.py ──→ public/<slug>/manifest.json
  └─ scripts/generate_books_index.py ──→ public/books.json
```

`./setup.sh` runs the whole chain per book registered in `books.json`
(`--book <slug>` limits the run to one book; `--deps-only`, `--skip-omr`,
`--skip-tei`, `--skip-images`, `--skip-manifest` still work and apply to
every book); every step is re-runnable.
`generate_tei.py` regenerates `public/<slug>/tei/` from scratch and refuses to
keep any file that fails Relax NG/Schematron validation.

Which homr implementation runs is selectable: the installed release by
default, or a local checkout via `run_homr.py --homr-path` (or `HOMR_PATH`,
honored by `setup.sh` too). `scripts/fetch_homr.py` (re)creates the
vendored development checkout from GitHub into `vendor/` (gitignored,
nothing installed); `run_homr.py` adapts to both the released and the
development homr API. This project currently runs the dev checkout (see
README for the measured differences).

## 5. Porting notes (other books, other OMR engines)

- Replace `run_homr.py` with any source of `{bbox, grid}` per staff plus a
  MusicXML file — everything downstream only needs `data/<slug>/results.json`
  (same shape) and the `pageNNN.musicxml` next to the scans. If you stay on
  homr, prefer a pinned checkout over a floating release for reproducibility.
- Keep the two TEI invariants: score files embed `score-partwise` with
  `xmlns=""` (add it at the source, as `run_homr.py` does), and staff
  geometry stays pixel-based in `surface`/`zone`/`path`. The embedded
  score is opaque to the TEI schema by design: switching the OMR source
  (different zone counts, no DOCTYPE, reordered MusicXML elements) needed
  no schema change here.
- Set `--base-url` on `generate_tei.py` and `generate_manifest.py` so the
  TEI `corresp`/`graphic` URLs match the deployed manifest (`--book-title`
  and `--label` set the TEI header title and the manifest label).
- Known MusicXML caveat: this OMR source can emit `<note>`s carrying both
  `<chord/>` and `<rest/>` (see `NOTES.md`). The official XSD accepts that
  combination syntactically (it is a prose-level, not schema-level rule),
  so XSD validation stays report-only and the viewer sanitizes the XML
  before rendering. Fix the source transcription to promote this layer to
  a hard gate.
